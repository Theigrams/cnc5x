## P1 `schedule` 里进给包络的启发式【已定方案 A】

**现状**：`cnc5x/scheduler.py` 的 `schedule(..., envelope=(s_env, v_env), split_rounds=10)` 让 block 内部也不超过进给包络，做法分三步：

1. 每个 block 的巡航上限取块内包络的**最大值**（`_block_caps`）；
2. 按插补周期采样，找出超出包络的 block，在超出比最大处加一个连接点，重新规划，最多 10 轮（`_worst_violations`）；
3. 仍然超出的，整条轮廓整体放慢（`envelope_scale`）。

相关代码约 90 行：`schedule` 中 `envelope` 分支、`envelope_scale`、`_envelope_ratio`、`_block_caps`、`_worst_violations`。

**问题**：

- 这套逐轮加连接点的做法不是来自任何一篇论文，是 Gemini 自己拼出来的启发式，收敛性没有保证（docstring 自己也写了"可能收敛得慢"）。
- 效果也不好：`examples/five_axis.py` 第 6、7 步里，走包络方案之后 C 轴 jerk 仍然超限，再整体放慢，用时比第 5 步只整体放慢**更长**。原因是包络只含匀速部分，切向 jerk 引起的 `q_s·j` 项它管不到。
- 用户对五轴进给规划还没有调研，不确定这部分以后是否需要。

**但包络不能整个删掉**：`CurvePath` 只在曲率峰值处设连接点限速，曲率近乎恒定的长区段（例如整圆）没有峰值，block 内会以 v_max 巡航而超出法向加速度限制。`tests/test_toolpath_scheduler.py::test_envelope_bounds_feed_on_full_circle` 守的就是这种情况。平面加工也需要"block 内部不超过几何限速"。

**方案**（2026-09-27 用户选定 A，B、C 留作记录）：

- **A. 换成保守的单遍做法**（推荐）：
  1. 每个 block 的巡航上限 `cap_i` 取块内包络的**最小值**（块内样本加两端插值）；
  2. 每个连接点的上限再与相邻两个 block 的 `cap` 取小；
  3. 双向扫描 + 每个 block 一段 S 曲线，与不给包络时完全相同。

  S 曲线在 block 内的速度介于两端速度和峰值之间，三者都不超过 `cap_i`，所以进给在包络样本上处处不超限，不需要迭代，也不需要整体放慢。代价是偏保守：包络在 block 内起伏大时，整段都按最低处走。以后需要时，可以在包络的局部极小处加连接点来缓解，但那是另一条改进，不在这次做。删掉 `split_rounds`、`_worst_violations`、`envelope_scale`、`_envelope_ratio`。
- **B. 保持现状**，只在 docstring 和 README 里标明这是未经文献验证的启发式。另外要修一个小漏洞：`_envelope_ratio` 用 `np.arange(0.0, profile.duration, Ts)` 采样，不含终点 t = duration。
- **C. 把包络分支整个移出 `schedule`**：放到 `examples/` 或以后的某篇论文里；整圆的情况则由 `CurvePath` 自己把 block 的巡航上限设成块内几何限速的最小值。

不论选哪个，`feed_envelope`（沿弧长采样进给上限）、`limits.drive_limit`、`limits.time_scale_factor` 都保留。它们概念清楚、各十来行，是五轴进给规划的基础构件（见仓库概览"五轴进给规划的现状"）。

**影响范围**（选 A 或 C 时）：

- `cnc5x/scheduler.py`、`cnc5x/__init__.py`（`envelope_scale` 的导出）；
- `tests/test_toolpath_scheduler.py`：`test_envelope_bounds_feed_on_full_circle`、`test_envelope_with_drive_limits`；
- `examples/five_axis.py` 第 6、7 步；
- `notebooks/04_S曲线与前瞻.ipynb`、`notebooks/06_五轴与机床轴.ipynb` 中用到 `envelope=` 或 `feed_envelope` 的单元格；
- `README.md` "各轴约束"一段；`docs/数学约定.md` 第 3 节"进给包络"；`docs/路线图.md` 第 2 节；
- `docs/入门报告/04_*.md`、`06_*.md` 与 `figures/make_ch04.py`、`make_ch06.py`（按 CLAUDE.md 第 10 节，入门报告在接口改完后统一检查一次即可）。

**验收**：

- 新增一条测试：随机包络上，规划出的进给在所有插补周期样本上不超过包络，且无需整体放慢；

## P2 限速参数的位置顺序不一致

**现状**：同一组参数（插补周期 Ts、刀尖进给的 v_max、a_max、j_max）在各函数里的位置不同：

| 函数 | 签名 |
| --- | --- |
| `scheduler.schedule` | `(path, v_max, a_max, j_max, Ts, phases=7, envelope=None, split_rounds=10)` |
| `ToolPath.get_v_limit` | `(Ts, v_max, a_max, j_max)` |
| `scheduler.feed_envelope` | `(path, s, Ts, v_max, a_max, j_max, chord_error, machine=None, drives=None)` |
| `limits.geometric_limit` | `(curvature, chord_error, Ts, a_max, j_max)` |

README 第 52、53 行相邻两行的示例里，`0.001`（Ts）一个在第 3 位、一个在第 5 位。传错不会报错，只会得到错误的数字。

**方案**：

- 在 `limits.py` 里、`DriveLimits` 旁边新增 `FeedLimits` dataclass，字段与 `DriveLimits` 同名：`velocity`、`acceleration`、`jerk`，都是标量，单位 mm/s、mm/s²、mm/s³（`along="axis"` 时为 rad/s…）。
- **流水线层**的函数改为接收 `FeedLimits`，`Ts` 和 `chord_error` 一律用关键字参数：
  - `schedule(path, feed, *, Ts, chord_error=None, phases=7, envelope=None)`（`chord_error` 的去留见 P4）；
  - `feed_envelope(path, s, feed, *, Ts, chord_error, machine=None, drives=None)`；
  - 连接点限速的新接口见 P4。
- **公式层**的函数保持标量参数，因为它们直接对应教材公式，拆开写更好读：`geometric_limit`、`chord_error_limit`、`curvature_limit`、`seven_phase`、`five_phase`、`bidirectional_scan`、`reachable_velocity`。只统一顺序：先是几何量，然后是限值，Ts 放最后或改为关键字参数。由实施的会话定一个规则，写进 `limits.py` 的模块 docstring。

## P3 两篇论文的 `chord_error` 其实是拐角容差（需核对原文）

**现状**：

- `papers/Zhao2013/algorithm.py`：`SmoothedPath(points, chord_error, c1)` 里的 `chord_error` 用在 `compute_d2` 的 `d2 = 2·chord_error / sin β`（式 (5)），它是**拐角逼近误差的上限**，不是插补的弓高容差。
- `papers/Xu2018/algorithm.py`：`CcrPath(points, chord_error)` 同样，用在式 (4) 的 `3·chord_error / cos(α/2)`。
- 两者的 `get_v_limit` 又把各拐角的**实际逼近误差** `self.chord_errors` 当作弓高容差传给 `geometric_limit`。这是"沿用原复现"（`~/Desktop/github-repo/cnc_interpolation`）。

**问题**：

- 命名违反 CLAUDE.md 第 7 节：拐角容差叫 `tolerance`，`chord_error` 只指插补的弓高容差。
- 把逼近误差当弓高容差，会在近直行的拐角上把速度压得很低。README 记录了这个现象：Xu2018 在 griffen 上有 19 个近直行拐角被压到 39–98 mm/s，逼近误差在 1e-13 mm 量级。两篇 README 都写了"是否符合原文有待核对"。

**方案**：

1. 查两篇原文的连接点限速公式（Zhao 2013 式 (16)，Xu 2018 对应部分），确认弓高容差到底取什么。论文 PDF 可在 `/Users/theigrams/Desktop/五轴CNC插补/五轴复现/Xu2018_IJAMT/` 找；Zhao 2013 不在该目录，需要用户提供，或用 paper2 技能查题录。
2. 构造参数改名为 `tolerance`；如果原文另有插补弓高容差，就再加一个 `chord_error`，与库里的 `HermiteCornerPath(points, tolerance, chord_error)` 保持一致。
3. 核对结果写进两篇的 README "与原文的差异"一节，并删掉"有待核对"的字样。

**影响范围**：

- `papers/Zhao2013/`、`papers/Xu2018/`（`algorithm.py`、`README.md`）；
- `tests/test_papers.py`、`examples/corner_smoothing.py`、`notebooks/05_拐角光顺.ipynb`；
- README 第 109–112 行（该段按 P10 移到论文 README）；
- `docs/入门报告/07_*.md` 中引用这两个类的地方。

**验收**：改名后测试通过；两篇 README 写明核对结论及依据（原文页码或公式号）。若原文无法获得，就如实写"未核对"。

## P4 `get_v_limit` 的重复与 `chord_error` 双处给定

**现状**：

- 五个 `get_v_limit` 实现中，有四个的结构完全相同：`geometric_limit(self.curvature_peaks, 容差, Ts, a_max, j_max)`，然后首尾补 0、再与 v_max 取小。它们在：
  - `cnc5x/toolpath.py` 的 `HermiteCornerPath.get_v_limit`、`CurvePath.get_v_limit`；
  - `papers/Zhao2013/algorithm.py`、`papers/Xu2018/algorithm.py` 的 `get_v_limit`。

  第五个 `LinearPath.get_v_limit` 物理含义不同：拐角处速度突变，`v ≤ a_max·Ts / (2 sin β)`，而且不用 `j_max`。
- `scheduler.py` 的 `schedule` 里又与 v_max 取了一次小（`limit = np.minimum(path.get_v_limit(...), v_max)`）。
- `chord_error` 在 `CurvePath(curve, chord_error)`、`HermiteCornerPath(..., chord_error)` 构造时给一次，调用 `feed_envelope(..., chord_error=...)` 时又给一次，两处没有一致性检查（README 的示例就是两处各写 `1e-3`）。
- 于是刀路这个几何对象带上了调度参数，而 Ts、a_max 又在调度时才给，两类参数分在两处。
- `tests/test_interpolator.py` 的 `SingleCurve` 也实现了一个 `get_v_limit`。

**方案**：

- 刀路只提供连接点的几何事实。建议：
  - 属性 `junction_curvature`，形状 `(n_blocks − 1,)`，即各内部连接点的曲率（`CurvePath`、`HermiteCornerPath` 现在叫 `curvature_peaks`，两篇论文也是）；
  - 首尾两个连接点的速度默认为 0。
- 连接点限速只写一份，放在 `scheduler.py`：由 `junction_curvature`、`FeedLimits`、`Ts`、`chord_error` 算出 `(n_blocks + 1,)`，首尾补 0，只在这里与 v_max 取小一次。`chord_error` 在调度时传入（`schedule(..., chord_error=...)`），与 `feed_envelope` 共用同一个值，刀路构造时不再给。
- 物理含义不同的刀路另外提供连接点速度上限，例如 `LinearPath` 的拐角速度突变。建议用一个可选方法（例如 `junction_limits(feed, Ts)`），`schedule` 发现刀路有它就用它，没有就用默认的曲率限速。具体接口由实施的会话定，但要满足：
  - 不引入 ABC；
  - 默认情况下子类什么都不用写。
- 如果 P3 的结论是两篇论文确实用逐拐角的容差，就让它们也走"另外提供连接点速度上限"这条路。
- 改完后更新 CLAUDE.md 第 3.6 条（刀路接口），删掉"计划重构"的字样。

**影响范围**：

- `cnc5x/toolpath.py`、`cnc5x/scheduler.py`；
- `papers/*/algorithm.py`；
- `tests/test_interpolator.py`（`SingleCurve`）、`tests/test_papers.py`（直接调用了 `get_v_limit`）；

## P5 插补的输入与周期对齐耦合

**现状**：

- `cnc5x/interpolator.py` 的三个入口 `interpolate`、`taylor_interpolate`、`correction_interpolate`，开头都重复同样三行：`align_period(profile, Ts)` → 算周期数 n → 按 `k·Ts` 采样。
- `align_period` 调用 `profile.scaled`，所以插补器实际依赖进给轮廓的四样东西，而不是 CLAUDE.md 第 3.5 条说的三样。
- 逐周期直接产生 s_k 的调度方法（例如 Beudaert 2012 的 VPOp）不产生 `Profile`，现在接不进插补器。
- 另外三个入口的输入和返回不一致：`interpolate` 收 `ToolPath`、返回 `Commands`；另外两个收单条 `Curve`、返回 `(u, 位置)`。

**方案**：

- 在 `profiles.py` 增加 `sample_feed(profile, Ts)`：先对齐到整数个周期，再采样，返回 `(t (N,), feed (4, N), scale)`。
- 插补的核心改为接收进给栈：`interpolate(path, feed, machine=None, branch=None)`。核心就是 `compose(path.derivatives(feed[0]), feed[1], feed[2], feed[3])` 加上机床轴。
  - `Commands.t` 由调用者给出，或由 `feed` 的列数与 Ts 算出，由实施的会话定；
  - `Commands.scale` 挪到 `sample_feed` 的返回值里。
- `taylor_interpolate`、`correction_interpolate` 同样改为接收进给栈。两者是"单曲线的教学对照"，返回值可以保持 `(u, 位置)`，但要在 docstring 里互相引用、说明与 `interpolate` 的区别。
- 改完后把 CLAUDE.md 第 3.5 条的"现状"一句删掉。

**影响范围**：

- `cnc5x/interpolator.py`、`cnc5x/profiles.py`、`cnc5x/__init__.py`；
- `tests/test_interpolator.py`（`test_taylor_interpolation_fluctuation` 里自己算了一遍对齐，可以直接改用 `sample_feed`）及其他调用 `interpolate(` 的测试；
- `examples/`、`notebooks/02`、`04`、`05`、`06`、`README.md` 快速上手；
- `docs/数学约定.md` 第 5 节。

**验收**：

- 三个入口不再有重复的对齐代码；
- 插补结果与改动前逐点相同；
- 新增一条测试：手工构造一段逐周期的进给栈（不经过 `Profile`）也能插补。

## P6 `feed_envelope` 缺入口检查（潜伏 bug）

**现状**（`cnc5x/scheduler.py` 的 `feed_envelope`）：

1. **刀路按刀轴转角计量**（`PoseCurve(..., along="axis")`）时，s 的单位是 rad。这时 `kappa = |tip_ss|` 不是曲率，而是对 rad 求导，单位也不对；它和 mm 计的 `chord_error` 相乘，得到的 rad/s 再和 mm/s 的 `v_max` 取小。这违反 CLAUDE.md 第 3.8 条。当前库内的调用都用默认的 `along="tip"`，所以还没有触发。
2. **只给 `machine` 不给 `drives`**：各轴约束被静默忽略。**只给 `drives` 不给 `machine`**：在 `None.axis_motion` 处报出看不懂的 `AttributeError`。

**方案**：

- 在入口检查刀路的计量方式，按刀轴转角计量时报错，报错信息指向 `docs/路线图.md` 第 1 节（纯转刀轴段）。检查需要刀路能回答"按什么计量"：
  - 建议 `PoseCurve` 保存 `along` 属性；

## P7 `Curve.measured` 让五轴概念进入基类（潜伏 bug）

**现状**：

- `cnc5x/curves.py` 的 `Curve` 有类属性 `measured = slice(None)`，基类的 `speed` 和 `speed_derivatives` 只用这几个分量算弧长。
- `PoseCurve`（`cnc5x/toolpath.py`）把它设为 `slice(0, 3)` 或 `slice(3, 6)`。
- `SubCurve`、`Reparameterized` 在构造函数里手工复制 `self.measured = curve.measured`。
- 以后任何包装 6 维曲线的新类如果漏了这一句，弧长就会把刀尖的 mm 和刀轴的 rad 混在一起取模，而且不会有任何提示。
- `PoseCurve` 还同时有 `measure`（计量用的那条曲线）和 `measured`（切片），两个名字只差一个字母。

**方案**（推荐第一种）：

1. **包装作用在分量上**：
   - 给 `Curve` 加一个方法 `restrict(a, b)`，默认返回 `SubCurve(self, a, b)`；
   - `PoseCurve.restrict` 返回 `PoseCurve(position.restrict(a, b), orientation.restrict(a, b), along)`；
   - `CurvePath`、`HermiteCornerPath` 里的 `SubCurve(curve, a, b)` 改为 `curve.restrict(a, b)`。

   这样 6 维的导数栈只在 `PoseCurve` 这一层出现，`curves.py` 完全不必知道五轴。接着删掉 `measured`，由 `PoseCurve` 自己覆盖 `speed_derivatives`（它已经覆盖了 `speed`、`length`、`length_at`、`u_at_length`）。

   目前 `Reparameterized` 只用在刀轴分量上（`pose_spline`），`SubCurve` 作用于 `PoseCurve` 的只有 `toolpath.py` 里的两处：`HermiteCornerPath` 的 `halves`，以及 `CurvePath` 的 `blocks`。
2. **最小改动**：把属性换成方法 `measured_part(x)`，包装类委托给内层曲线。风险和现在一样，都是包装类必须记得委托，只是名字更清楚。不推荐。

**影响范围**：

- `cnc5x/curves.py`、`cnc5x/toolpath.py`；
- `tests/test_curves.py`、`tests/test_toolpath_scheduler.py`；
- `docs/入门报告/05_库的设计一_曲线导数与弧长.md` 第 602 行附近专门讲了 `measured`，需要改写；
- `docs/数学约定.md` 第 2 节（弧长计量）。

**验收**：

- `grep -rn measured cnc5x` 为空；
- 五轴刀路的弧长、`derivatives_by_length` 与改动前一致；
- 新增一条测试：对 `PoseCurve` 取子段后弧长仍只量刀尖。

## P9 "是否五轴"的判断散在五处

## P11 零碎问题

每条都很小，可以随时顺手做，也可以攒几条一起做。

1. **`scheduler.py` 的 `schedule` 里变量名 `knots`**：它指 block 分界的弧长位置，而全库其他地方的 `knots` 都指 B 样条节点。改名为 `junctions`，与 docstring 里的"连接点"一致。

4. **`curves.py` 的 `ArcLengthTable.s`、`ArcLengthTable.u` 没有 docstring**，补两行。

8. **`toolpath.py` 的 `ToolPath.derivatives` 每次调用都重建 `curves` 列表和累积长度**，属于微性能问题。插补时只调用一两次，暂不处理；如果以后逐周期调度要频繁调用，再缓存。
9. **`fitting.py` 求基函数矩阵有两条路径，理由没写**：
   - `interpolate_bspline` 用稀疏的 `si.BSpline.design_matrix`；
   - `fit_bspline` 和 `condition_rows` 用稠密的 `basis_matrix`（把单位矩阵当控制点）；
   - `condition_rows` 还对每个条件单独建一次 `BSpline`。

   两条路径并存是有原因的：SciPy 的 `design_matrix(x, t, k, extrapolate)` 不能求导数，导数条件只能走 `basis_matrix`；插值的方阵在几千个点时用稠密矩阵太大。按 CLAUDE.md 第 5 节"两种处理并存时写明理由"，在两个函数的 docstring 里写明这一点即可。`condition_rows` 的逐条构建可以改为按导数阶数分组、一次求值，是否值得由实施的会话判断。
10. **弧长表多算了一次速度**：`curves.py` 中 `ArcLengthTable.__init__` 最后的 `speed = curve.speed(self.u_grid)`，求的是网格端点的速度。这些值在最后一轮 `_piece_errors` 里已经作为各段端点（`sa`、`sb`）求过，只是被丢掉了。属于微性能问题；要改就让 `_piece_errors` 把端点速度一起返回。
11. **`interpolate_bspline`（拟合）与 `interpolate`（周期插补）动词相同、含义不同**。The NURBS Book 把过点拟合叫 interpolation，所以不必改名；在两者的 docstring 里各加一句区分，并在 CLAUDE.md 第 7 节的术语表里写明。
12. **术语待核对**：
    - `seven_phase`、`five_phase` 的 "phase"：另一份评审认为国际文献的通行叫法是 seven-segment / five-segment S-curve，这一点**尚未核对**。按 CLAUDE.md 第 7 节，先查 CIRP / IJMTM 上的用法（例如 Erkorkmaz & Altintas 2001），再决定是否改名。改名会牵动全仓库，最好与 P2 一起做。
    - `feed`（`Commands.feed`、`feed_envelope`）与 `feedrate`（`metrics.feedrate_fluctuation`）混用。在术语表里写明分工，或统一成一种。
